# Profile Pilot M2 v0.5.1 Implementation Plan

> **For agentic workers:** Execute one Task at a time. Use TDD for production behavior, preserve every failed or inconclusive Pilot outcome, and use isolated Sub-agents only for immutable Subject Dispatches or anonymous Review Packets.

**Goal:** 為 C#、Python、TypeScript 與 React 四個 Experimental Profile 建立可重跑的 M2 Pilot，公開 34 組完整結果與限制，並只將有增量實證的 Profile 升級為 `beta`。

**Architecture:** 沿用單一 `evals/harness/`，將 v0.3.0 的固定 Campaign 改為 Manifest-driven，同時用 Legacy Contract Tests 鎖住既有 36 組歷史行為。公開 Fixture Repository 新增四個 Scenario，與既有四個 Candidate Scenario 組成 `profile-pilot-v1`。M2 Manifest 以 Scenario-specific Arms 產生 34 個隔離 Subject Runs，再由匿名 Reviewer 與 Controller-owned Outcome Builder 建立公開 Result。Profile Metadata 以 Result Path、SHA-256 與交叉驗證後的 Outcome 作為唯一成熟度證據。

**Tech Stack:** Agent Skills specification、Markdown、YAML、JSON Schema Draft 2020-12、Python 3.12 `unittest`、PyYAML 6.0.3、jsonschema 4.26.0、.NET 8、Node.js 24、TypeScript、React、Vitest、FastAPI、GitHub Actions、Git。

**Spec:** `docs/superpowers/specs/2026-09-04-composable-language-framework-profile-architecture-design.md`

## Completion Contract

- **目標成果：** 公開且可稽核的 `profile-pilot-v1` Fixture Tag、34 組完整 Pilot Result、四個 Profile Outcome、Metadata Evidence Link 與雙平台 CI。
- **範圍：** C#、Python、TypeScript、React；Harness 泛化；八個 Fixture；Pilot Repetition 1；匿名 Review；Evidence 與成熟度更新。
- **排除：** Full Run、`stable`、Go／Rust／Java／Vue Reference、Specialist Package 發布、目前 Repository 的 Merge、`v0.5.1` Tag 與 GitHub Release。
- **完成條件：** 34 個 Slot 都有 Terminal State；Profile Outcome 可重算；兩個 Repository 的授權 Push 完成；Fixture Tag 與開發分支 CI 成功。
- **終點層級：** Fixture Repository Branch／Annotated Tag 公開，Skill Repository 開發分支公開；停止在 Merge 與 Release 前。

## Global Constraints

- Skill Repository 使用已建立的 `codex/v0.5.1-profile-pilot` 隔離 Worktree；Fixture Repository 使用另一個 Repository-sibling 隔離目錄與 `codex/profile-pilot-v1` Branch。兩個 Repository 不共享工作樹或 Staging Area。
- 受測 Skill 固定為 Tag `v0.5.0` 與 Commit `bd895776a80566381003182bfdb24f0f02784731`。開始 Pilot 後不得修改受測 `SKILL.md` 或四份 Profile Reference，再把修改後內容冒充同一 Treatment。
- Fixture 固定為新的 `profile-pilot-v1` Annotated Tag。正式 Stage 前先驗證 Tag 指向 Commit、Fixture Tree Hash、Lockfile Hash、Evaluator Hash 與 Prompt Hash。
- Subject 固定使用 `gpt-5.6-sol`、`high`、`codex-desktop-collaboration`、`desktop-subject-v4`、480 秒 Timeout 與 `fork_turns: none`。每個 Run 使用新的隔離 Agent Context。
- Anonymous Reviewer 固定使用 `gpt-5.6-terra`、`max` 與 `fork_turns: none`。每個 Scenario 使用一個新的 Reviewer，只能讀取該 Scenario 的匿名 Packet；不得取得 Arm Mapping、Subject Thread ID 或其他 Scenario 結果。
- 同時最多執行兩個 Subject 或兩個 Reviewer，避免超過工作目錄、Agent Slot 與人工驗收能力。每個 Agent 都只擁有自己的 Workspace 或 Review Packet。
- Controller 不得略過失敗 Run、選擇性重跑弱結果或在解盲後更改 Criteria。Retry 只接受既有 `harness_error`、`dependency_cache_error`、`cli_runner_error`、`environment_error`，每個 Physical Attempt 最多重試一次並保留原始證據。
- `control` 與 `generic-clean-code` 不暫存 Skill。所有 Core／Treatment Arms 暫存相同 `v0.5.0` Core Package；Prompt 與必須查閱的 Reference 是 Arms 間唯一刻意改變的條件。
- `v0.1.0`、`v0.2.0`、`v0.3.0` 與 `v0.4.0` Manifest、Result、Receipt、Fixture Tag 與歷史 Diff 不得修改。
- Fixture、Evaluator、Prompt、Allowed Diff、`incremental_criteria` 與 Rubric 必須在第一個 Subject Stage 前 Freeze。任何後續契約變更依 Scenario 全 Arms 作廢，不能只重跑單一 Arm。
- C# Fixture 的必要 Public Type／Property 使用繁體中文 XML 註解；所有文件、測試資料與註解保持 UTF-8，不放入雇主、校務、學生或內部 Repository 資訊。
- 不使用 Recursive Delete。所有工作區與產物使用尚不存在的唯一目錄；失敗清理只處理本次明確建立的單一檔案或空目錄。
- 每個實作 Task 依序完成 RED、最小 GREEN、Targeted Regression、`git diff --check` 與 Conventional Commit。Worker 只提供交付，Sol 負責最終 Diff、測試、Evidence 與安全驗收。
- Push Fixture Branch／Tag 與 Skill 開發分支已獲授權。Merge、目前 Repository Tag、GitHub Release 與 Specialist Package 發布仍未授權。

- [ ] **Step 6: 寫 Pre-execution Freeze RED Tests**

Manifest 新增可驗證的 Freeze Policy：省略時為 v0.3.0 的 `post_pilot`；M2 明確指定 `pre_execution`。固定下列狀態機：

1. v0.3.0 `freeze` 保留 Pilot 全部完成後才能建立 Receipt 的既有行為，Pilot Stage 仍只要求 Preflight。
2. M2 `freeze --phase pilot` 可在沒有 Subject Result 時建立 Pre-execution Receipt，但必須先通過 Preflight 與完整 Contract Hash 驗證。
3. M2 `stage --phase pilot` 在列出或建立任何 Subject Workspace 前必須驗證有效 Freeze Receipt；缺少 Receipt、Hash Drift 或已失效 Receipt 一律阻擋。
4. Freeze 後若 Manifest、Harness、Fixture、Evaluator、Prompt、Skill 或 Rubric Drift，必須保留舊 Receipt、另寫 Immutable Invalidation Receipt，禁止覆寫或刪除證據。受影響 Scenario 的全部 Arms 一律失效並要求新 Freeze；若 Drift 屬全域 Contract，八個 Scenario 全部失效。
5. 新 Freeze 不得讓舊 Freeze 下已 Stage／Collect 的 Run 重新成為有效證據，必須以新的 Contract Hash 與隔離 Attempt 身分執行。

- [ ] **Step 7: 最小實作 Manifest-defined Freeze State Machine**
