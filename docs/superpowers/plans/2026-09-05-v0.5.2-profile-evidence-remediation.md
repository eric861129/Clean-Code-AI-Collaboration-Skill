# v0.5.2 開發計畫與目標：Profile 查閱證據與比較組隔離

狀態：2026-09-05 已實作並完成協定 Canary 與正式 Pilot；2026-09-12 使用者核准正式發布 v0.5.2。設計與授權契約保留於本文件；實驗結論以公開 Result 為準，正式發布以 main、Tag、GitHub Release 及同一 SHA 的雙平台 CI 核對，不因發布改判實驗結果。

基準：`v0.5.1`／`4ce3a697eb7eea36ecddd937ffa915f931e9524a`。

適用範圍：評測 Harness、查閱紀錄契約、重現性、C#／Python／TypeScript／React 的新 Pilot。Core 的產品使用方式、Profile Routing 與成熟度定義仍以[原始架構 SPEC](../specs/2026-09-04-composable-language-framework-profile-architecture-design.md)為準；本提案只對新 Campaign 定義協定差異，不追溯修改 v0.5.1。

## 1. 版本目標與完成契約

**主要目標：讓完整且合法的查閱紀錄能通過證據驗證，阻擋比較組使用未指定 Profile，取得可重算的新一輪 Profile Pilot 結果。**

| 目標 | 可觀察成果 | 驗收門檻 |
| --- | --- | --- |
| G1 查閱證據正確判定 | 必讀、允許與禁止查閱分開建模 | 合法 Core 額外查閱通過；缺漏、錯誤 Hash、跨組 Profile、越界路徑被拒絕 |
| G2 比較組隔離 | Prompt、Dispatch、Report 使用同一組 Applied Profiles 與查閱政策 | Core Only 明確為空 Profile；React 的直接 Comparator 固定 TypeScript Only |
| G3 可重現執行來源 | Freeze 保存可從 Git 重建的執行版本與檔案 Hash | Ubuntu／Windows 重建同一份新 Contract；舊 M2 重播仍通過 |
| G4 全新 Pilot | 34 個新 Subject Slots、34 份新匿名 Review、4 個 Outcome | 所有 Slot 終止且無選擇性重跑；各 Outcome 可由相同證據重算 |
| G5 誠實交付 | Metadata、公開結果與安裝文件一致 | 只有新 Pilot `passed` 可支持 Beta；所有其他結果如實保存 |

工程成功不要求四個 Profile 都勝出。`no_difference` 或可歸因的 `failed` 都是有效實驗結果。目標是四個 Profile 都能作成可判定結論；若仍有 `inconclusive`，必須指出具體原因與受影響比較，不能為提高通過率放寬標準。

**完成層級分開記錄：**

1. 工程完成：協定、相容性、Fixture 與自動化驗證通過。
2. Pilot 完成：新 Campaign 全部終止、Review 齊備、Result 可重算。若有未排除的系統性協定缺陷，只能標示 Campaign 已終止，不能標示證據修復成功。
3. 公開交付：獲授權的 Fixture 與 Skill 開發分支推送完成，雙平台 CI 通過。
4. 正式發布：另按明確發布授權完成 Merge、`v0.5.2` Tag、Release 與公開回讀。

## 3. 方案選擇

| 方案 | 影響 | 決定 |
| --- | --- | --- |
| 保持 exact-set，只叫 Subject 少填查閱檔案 | 容易把真實查閱藏起來，也未處理 Core 必讀 Reference 的矛盾 | 不採用 |
| 必讀集合＋允許集合＋明確 Applied Profiles，完整記錄所有查閱 | 保留 Core 漸進式載入，能分辨合法補充與跨組 Profile | **採用** |
| 另建精簡 Core、各組專屬 Skill Package 或強制檔案代理服務 | 改變受測內容與執行環境，增加新的歸因變因及維護範圍 | 本版不採用 |

這次沿用單一 Harness，在明確的新協定版本加入上述契約。不是修改 v0.5.1 判定方式後重新發布同一份實驗。

## 4. 新協定設計

### 4.1 Arm 的單一設定來源

在 Manifest 的 Arm Contract 新增下列欄位，並由同一來源產生 Prompt、Dispatch、Template 與 Collector 規則：

- `applied_profiles`：本實驗指定使用的 Profile ID 清單。
- `required_skill_inspection_paths`：缺少任一項就不足以建立查閱證據。
- `allowed_skill_inspection_paths`：可如實回報的完整允許集合，必須含所有 required 路徑。
- `inspection_policy`：新 Campaign 為 `required-subset/v1`；歷史 Manifest 未宣告時保持原有 exact-set 行為。

集合在 Freeze 前展開為排序後的精確路徑，不允許執行期間以 Glob、目錄掃描或目前主分支內容擴大。合法 Core 集合由固定 Skill Commit 下、排除所有 Language／Framework Profile Reference 後的 Core Reference 清單建立；不能只排除已知四個 Profile，而忽略後續新增 Profile。建立集合時核對該來源的 Profile Metadata 與 Reference 分類。

| Arm | Applied Profiles | 允許查閱範圍 |
| --- | --- | --- |
| control | `[]` | 無 Skill Claims |
| generic-clean-code | `[]` | 無 Skill Claims |
| core-only | `[]` | Core 入口與 Core References，含 Profile Selection |
| core-plus-csharp | `[csharp]` | Core＋C# Reference |
| core-plus-python | `[python]` | Core＋Python Reference |
| core-plus-typescript | `[typescript]` | Core＋TypeScript Reference |
| core-plus-typescript-plus-react | `[typescript, react]` | Core＋TypeScript＋React Reference |

必讀最小集合沿用入口、Profile Selection 與各 Arm 指定 Profile；其餘 Core Reference 依 Task 實際需要讀取，不強迫全部載入。完整 Package 在所有 Skill Arms 中相同，不把 Bundled Profile 解讀成 Applied Profile。

### 4.2 Prompt 與查閱方式

新 Prompt 必須明確說明：這次的 Applied Profiles 是實驗指定值，Core Only 不執行自動 Profile 套用；React 的 TypeScript Comparator 不讀 React Reference。這是 Benchmark User Instruction，不改變一般 Consumer 的自動 Routing 行為。

Subject 應完整列出實際查閱的 Skill 檔案；不可為通過檢查省略額外檔案。允許集合也不能被理解為要求全部查閱。

提供 Benchmark 專用的唯讀查閱入口，建議 CLI 為 `inspect-skill`：讀取同一份 Dispatch、驗證指定路徑、輸出檔案內容與 SHA。它不替 Subject 完成任務、不預先填入成功 Claims、不自動補足未讀檔案。其用途是減少手抄路徑／Hash 錯誤，所輸出資訊仍是可核對的查閱紀錄，不是模型理解證明。

### 4.3 Collector 的判定順序

1. 驗證 JSON 結構、欄位型別與重複路徑。
2. 驗證 Path 為 Repository-relative POSIX、位於指定 Skill Root，拒絕 Traversal、Absolute Path、Symlink Escape。
3. 驗證所有 Claims 屬於 allowed，並獨立偵測禁止 Profile 的查閱紀錄。
4. 驗證 required 全部存在。
5. 驗證每一筆 Claim 的 SHA，包含合法額外 Core 檔案。
6. 核對 Report 的 `applied_profiles` 與 Arm 相同，並與 `files_inspected` 的 Skill 路徑互相核對，防止只在另一個欄位暴露跨組查閱卻未被發現。
7. 原有 Diff Boundary、完成狀態、Controller Oracle 與 Review Gates 仍照原規則執行。

同一報告有多個問題時，保存排序後的完整診斷清單，不只保留第一個錯誤。上層仍保留 `invalid_claim`／`skill_not_used` 等相容狀態，細節用穩定 Reason Codes，例如 `unexpected_skill_file`、`profile_contamination`、`missing_required_skill_file`、`skill_hash_mismatch`、`invalid_skill_path`、`duplicate_skill_claim`、`applied_profiles_mismatch`、`inspection_record_mismatch`。

Core 額外查閱全部合法且 Hash 正確時通過；Core Only 讀 Python／React 仍是無法支持直接比較的 Evidence Gap。不得靠忽略該檔案或刪除 Claim 使污染候選通過。

本版不為證據不合格的候選補跑 Oracle 來恢復比較資格；保留 `oracle_results` 為空並標明 `not_run_due_to_evidence_gate`。診斷用途的獨立 Oracle 如另行提出，必須與正式結果分開，不能回填舊 Run。

### 4.4 版本與輸出相容性

- 新 Desktop 協定為 `desktop-subject-v5`；舊 v4 的 Dispatch／Report／Freeze／Outcome 驗證維持不變。
- 新 Report、Dispatch 的 Schema ID 升版，明確載入對應解析器；缺欄位不得靜默套用新寬鬆政策。
- 新公開結果使用 `profile-pilot-result/v2`，新增安全的查閱診斷摘要、Oracle 未執行原因與 `execution_commit`。v1 原有 Schema 保留；新增 `evals/profile-pilot-result-v2.schema.json`，Validator 依白名單 Schema ID 選擇，不相信外部 URL。
- `scripts/validate_profiles.py` 與 Packager 同時支持 v1／v2，並追蹤實際使用的 Schema Input Hash。
- 公開資料只放必要的相對路徑／Reason Code／Hash；Agent 身分、私有 Mapping、Workspace 絕對路徑及原始對話留在私有證據。
- 匿名 Review Packet 移除會透露 Arm 的 Profile 名稱、查閱路徑與 Applied Profiles；只保留「證據 Gate 失敗」等中性限制。解盲後才在公開 Result 連接診斷摘要。

### 4.5 凍結與跨平台重現性

新 Campaign 必須在乾淨且已 Commit 的執行來源 Freeze，將 `execution_commit` 寫入 Receipt 與公開 Result。Manifest 在該 Commit 已存在；Commit 身分於 Freeze 時取得，避免 Manifest 自引用 Commit SHA。

完整契約包含實際執行到的 Harness、查閱 helper、Prompt Generator、Schema、Rubric、Arm Policy、Fixture、Skill 及必要共用模組。不可只 Hash 一個目錄而漏掉被匯入的外部程式碼。採明確的輸入檔案清單與相對路徑排序，兼容 Legacy Hash 演算法。

新 Fixture 使用 `profile-pilot-v2`：保留八個 Scenario 的任務、Allowed Diff、Oracle、Criteria 及依賴版本；只增加必要的換行契約，例如 `.gitattributes`，確保新的 Staged Text Bytes 固定為 LF。排序使用 POSIX 路徑與明確大小寫規則，避免依 Host OS 的 Path 排序。

新 Preflight 必須核對 Git Blob、實際 Staged Bytes、Evaluator Bytes 與 Freeze 值一致。歷史 `profile-pilot-v1` 不移動，v0.5.1 的 Windows CRLF 重播保持原樣。

Freeze 後任一執行輸入變更，保留舊 Freeze 並建立 Invalidation，不能以目前 Harness 冒充執行時來源。若只是必要的公開去識別修正，也要保存 publication transform 的來源版本與前後 Hash，不改變原始語意結果；遇到無法證明等價的變更，停止發布並另定新 Campaign。

## 5. 實驗設計與資源邊界

### 5.1 固定比較

正式 Pilot 沿用八個 Scenario、七種 Scenario-specific Arms、共 34 個 Slots，Repetition 為 1。所有 34 組都在新 Campaign 執行，不能只重跑舊失敗 17 組，不能混用 v0.5.1 的成功候選或 Review。

直接比較維持：C#／Python／TypeScript 各為 Core Only 對指定 Language Profile；React 為 TypeScript Only 對 TypeScript＋React。Control／Generic 只作背景。

建議固定 Subject 為 `gpt-5.6-sol`、`high`，Reviewer 為 `gpt-5.6-terra`、`max`，以減少相對前輪的模型變因。正式啟動前確認可用性；不可用時必須在 Freeze 前更新全 Campaign 設計，不能執行途中替換或假稱相同模型。

Skill Source 固定為已發布 `v0.5.1`／`4ce3a697eb7eea36ecddd937ffa915f931e9524a`，不使用持續修改中的 v0.5.2 Working Tree。本版不修改 Language／Framework Reference 語意；新證據對該固定來源的 Profile 有效，Suite 版本與受測版本分開保存。兩輪 Prompt、協定、Fixture 換行及 Skill Source 都有差異，因此不將跨版本通過率變化當成 Profile 效果增量。

沿用 Subject Timeout 480 秒、Fixture／Oracle Timeout 各 120 秒；新 Random Seed 固定為 `560502`，在看見正式結果前凍結。

### 5.2 先驗證協定，再開始正式 Pilot

Canary 是操作協定檢查，與正式效果評測分開 Manifest／Runs Root，不參與成熟度 Outcome。固定 11 組：

| Scenario | Canary Arms |
| --- | --- |
| csharp-overdue-rule | core-only、core-plus-csharp |
| fastapi-provider-boundary | core-only、core-plus-python |
| typescript-runtime-validation | control、generic-clean-code、core-only、core-plus-typescript |
| react-state-error-retention | core-only、core-plus-typescript、core-plus-typescript-plus-react |

Canary 驗收：全部報告可解析、合法 Core 額外查閱可通過、沒有意外跨 Profile、必要 Claims 與 Hash 完整；另以合成負例證明禁止讀取與錯誤 Hash 確實被拒絕。Canary 的行為 Oracle 可以失敗，不能為使其通過修改 Gold Behavior 或正式 Criteria。

若協定 Canary 失敗，先診斷並修正 Harness／Prompt，只允許再執行一批完整 11 組確認。兩批都保留，最多 22 組 Canary；仍不合格即停止正式 Pilot，回報阻擋與剩餘決策。不得持續改 Prompt 直到出現有利分數。

正式 34 組在通過 Canary、重新確認乾淨執行來源並 Freeze 後一次啟動。最大並行 2 個 Subject；Reviewer 等 Subject 收集完成後啟動，最大並行 2 個。每個 Subject 使用新隔離環境；八個 Scenario 分派八個新的匿名 Reviewer，每份候選獨立評分、不得相互排名。

正式 Subject 邏輯槽數固定 34。基礎設施重試沿用凍結 Retry Policy；Candidate Failure、污染或不利結果不重跑。每次實體 Attempt 都留 Receipt。Token／實際模型服務證明與網路隔離資訊若不可取得，照實標記，不把指定模型或自述當成額外 Telemetry。

## 8. 工作順序、分工與停止條件

相依順序：T0 → T1 → T2 → T3／T4 → T5 → T6 → T7 → T8。T3 與 T4 在共同契約固定後可分工，其他階段依相依關係執行，不同時修改同一個 Harness 核心檔案。

開發採「先建立能捕捉缺陷的測試，再作最小修正」。Controller 負責整合、來源 Freeze、Outcome 與授權核對；開發 Reviewer 與實驗 Subject／匿名 Reviewer 不混用 Context。進行多 Agent 開發時明確指定檔案 ownership，避免把 Review 授權誤當成任意修改權。

以下情況停止相依工作，仍可完成無關的已授權驗證：

- 兩批 Canary 仍出現協定缺口：停止正式 Pilot。
- Subject 模型／Client 無法維持固定條件：停止新 Dispatch，不靜默替代。
- Freeze 後來源漂移：保留失效證據，停止受影響 Campaign。
- 無法取得必要歷史來源／Fixture：重播 Gate 失敗，不改成 skip 冒充通過。
- 原始結果遭修改、匿名性洩漏、Outcome 不能重算：停止公開發布。
- 發現需要修改 Profile 內容才能改善分數：另定受測版本與實驗，不能混入這次協定修復。

沒有「反覆重跑直到四個 passed」的完成條件。正式 Pilot 若暴露新問題，完整保存結果並明列工程／實驗完成層級，停止擴張本版。
